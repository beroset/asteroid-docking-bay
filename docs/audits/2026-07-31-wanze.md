# wanze — building a probe that measures a watch without changing it

**Date:** 2026-07-31
**Scope:** design and first hardware bring-up of `wanze`, the on-watch
telemetry probe, plus its host-side reader in a-d-b.
**Hardware:** nemo (`604KPMZ003491`, MSM8926) and catfish (`720EX91190639`),
both on the w541 rig, both handed over explicitly for this work.
**Status:** v0.1 running on both watches. **The central precondition is still
unmet** — see "What is not established" at the end. Nothing wanze produces
should be quoted as fact yet.

## Why this exists

Every battery figure this project has is a *docked* figure. A drain test means
shelving a watch on the rig and measuring a standby nobody actually
experiences, and a watch that is never docked cannot be measured at all. Worse,
the one question a co-maintainer actually asked — does bringing CPU cores
online destroy battery life? — is answered today from recollection rather than
from numbers.

A probe that records on the watch and is read at the dock closes that. The
catch is that it has to be cheap enough to leave installed on a watch somebody
is *wearing*, which is a much harder constraint than it first appears.

## The design decision everything else follows from

The obvious implementation is a sampling daemon on a timer. That is the wrong
answer, and the reason is worth stating plainly:

> On a watch, the expensive part of a periodic job is **the wakeup**, not the
> reading.

A handful of sysfs reads costs nothing. Waking the CPU out of suspend every
minute to perform them costs a great deal. A probe built that way would be
draining the battery it claims to measure — the purest form of the failure mode
this project keeps rediscovering.

So the rule is: **never wake the watch; record only when something else already
did.** In practice that is a `systemd` timer with `WakeSystem=false` firing a
`Type=oneshot` service that appends one line and exits. Such a timer arms no
RTC alarm. `AccuracySec` is set deliberately sloppy (5 minutes) so systemd can
coalesce the firing with wakeups that were happening anyway. Nothing is
resident between samples: no loop, no wakelock, no process to leak.

The apparent cost is that samples become irregular and full of holes. That is
the second half of the design rather than a defect:

> **A gap means the watch genuinely slept through it.** That is exactly the
> standby behaviour we want to measure, and exactly what a regular sampler
> destroys by waking through it.

A trace that is 90% holes is describing a very healthy watch.

## Method

1. Capability-probe both watches over adb — what exists, what is readable.
2. Build the sampler and units against what was actually found, not against
   what a Linux box usually has.
3. Install on both, confirm the timer fires unattended.
4. Cut VBUS to catfish **while it kept running**, to produce a genuine
   off-charge trace with real sleep gaps.
5. Build the host-side reader with tests, each validated by planting the bug it
   exists to catch.

## What the hardware said

| | nemo | catfish |
|---|---|---|
| suspend supported (`/sys/power/state`) | `freeze mem` | `freeze mem` |
| suspend actually observed this boot | 0 (docked, charging, screen lit) | **6** |
| systemd | 257 | — |
| gauge node | `battery` | `nanohub_fuelgauge-0` |
| `current_now` | **always 0** — no sensor | present |
| cores online | **1 of 4** | 4 of 4 |
| `/sys/class/backlight` | **absent** | absent |

Two of those changed the implementation. There is **no `/sys/class/backlight`**
on these watches — the panel appears under the LED class as
`/sys/class/leds/lcd-backlight`, so the obvious implementation would have
silently recorded an empty screen-state column forever. And nemo having one of
four cores online is a direct corroboration of the earlier underclock finding
that the offline cores, not the GPU pin, are where the performance went.

Timer firing was confirmed unattended on nemo: `uptime` 661.68 → 996.54 across
one interval, with no intervention.

## Defects found

### W1 — the watch clock is not trustworthy (critical)

Measured against the host at the same moment:

| watch | wall-clock error |
|---|---|
| catfish | **130 days behind** |
| nemo | **~2 hours ahead** |

Both were recording perfectly well. This is not a broken watch; it is the
normal state of a device that has not synced.

Consequently **every timing figure comes from `uptime`**, which no clock
adjustment can move, and `epoch` is kept only as a host anchor. The skew is
measured at harvest and **reported rather than corrected** — a fixed-up
timestamp looks trustworthy, and a visibly wrong one does not.

There is a subtlety here that nearly produced a decoration test. A *constant*
offset is harmless to deltas: epoch-based and uptime-based timing agree exactly
on a steadily-wrong clock. So a test built around catfish's 130-day skew passes
against an implementation that uses the wrong clock entirely — which is what
happened on the first attempt. The discriminating cases are a clock **stepped**
mid-trace (would invent hours of standby that never happened) and a clock
**frozen** across suspend (would hide real sleep). Both are now tests, and both
fail against the planted bug; the original skew test remains, relabelled to say
what it does and does not prove.

### W2 — `/sys/power/wakeup_count` blocks (high)

Reading it hangs, by design, until the kernel can capture the count. It hung
the first capability probe *completely* — the script returned no output at all,
not even the fields it had already gathered.

The sampler never reads it. `wanze.service` carries `TimeoutStartSec=30` as a
backstop, and the general lesson is now applied to probe scripts: **time out
each read individually**, so one blocking node costs one field rather than the
whole probe.

### W3 — catfish's two battery nodes disagree (medium, open)

`/sys/class/power_supply/battery` reported `capacity=50` while
`nanohub_fuelgauge-0` reported `100`, at the same instant. Both a-d-b and wanze
resolve `nanohub_fuelgauge-*` first, so they agree with each other — but if the
50 is the true figure they are wrong *together*, which is the least visible
kind of wrong.

**This is a watch-side question and is not resolved here.** Flagged for mo.

## Testing

17 host-side tests, all validated by planting the bug they exist to catch:

| planted bug | caught by |
|---|---|
| gap detection from `epoch` instead of `uptime` | 4 tests, including the two clock-divergence cases added specifically because the original skew test did **not** catch it |
| reboot detection disabled (uptime drop ignored) | `test_an_uptime_drop_splits_the_trace` |

Sensor classification is **not** reimplemented: the parsed rows use the key
names `drainlog` already understands, so its per-watch sign learning and
always-zero detection cover both formats. That is the "consolidate rather than
add" rule doing real work — the alternative was a second, subtly different
copy of the hardest logic in the codebase.

## What is not established

**wanze has not proven that its own battery cost is negligible.** The A/B — one
watch, wanze installed versus not, refereed by a real drain test — has not been
run. Until it has, every number wanze produces is provisional.

This is the precondition that can kill the design, and it is stated first in
the spec for that reason. An instrument that changes what it measures is worse
than no instrument, and here it would do it to itself. The honest position is
that the *architecture* is defensible on first principles and the *overhead* is
unmeasured.

Also outstanding: the bounded ring buffer has been implemented but not
exercised against a genuinely long undocked period, and the long off-charge
trace from catfish was still running when this was written.

## Dead ends and corrections

- The first capability probe returned **nothing at all** and was assumed to be
  an adb problem. It was not — `wakeup_count` was blocking. Bisecting with
  per-command timeouts found it in one pass; guessing would not have.
- A "one row after 20 minutes" result on nemo was briefly read as the timer
  failing. It was arithmetic on my part: only one interval had elapsed. The
  timer was healthy and `systemctl list-timers` said so.
- The first wiring test for the reconnect badge (same session, separate
  concern) passed against a tree with the wiring deleted, because setting the
  monitor's stop flag makes its read loop return on the first line. Rewritten
  and re-planted. Recorded here because it is the same failure shape as the
  clock test above: **a test that cannot fail is decoration**, and both were
  caught only by planting the bug.
