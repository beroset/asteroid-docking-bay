# Pre-1.0 deep audit — 2026-08-16

Autonomous overnight run, authorised by mo: bug hunt plus an architecture
revisit, with **redundancy as the explicit priority** — features were added
subsequently without always checking whether reusable code already existed.
The evening's window-handling consolidation (three drag mechanisms → one) is
the model for what to look for.

**Scope: code only.** The rig is not touched — mo is asleep, the `1-3` cascade
trips under sustained load, and sol/aurora belong to the porting session.

Baseline: branch `onboard-discovery-rework`, version `1.0dev`,
18,253 lines of package + 13,415 lines of tests, 805 tests green.

## Rules this audit holds itself to

- A consolidation must be **behaviour-preserving with existing tests passing
  unchanged**. That is the evening's standard ("the two existing drag tests
  pass unchanged, which is the point").
- If a change would require existing tests to be **rewritten** to pass, it is a
  finding for the morning, not a night action.
- Anything touching **flash, dump or power** paths is a finding, not a fix,
  regardless of confidence. An audit that rewrites the dangerous paths
  unattended is not an audit.
- One concern per commit; suite green, deployed and verified between each.

## Already known before this run

Carried in so the night is spent on what is not yet known:

  image: `sizeComposite` computes the width from the viewport, so the window
  fits the picture. Making it resizable means re-pointing that at the box.

### F1 · HIGH · the CLI could cut power on a locked watch — FIXED

`asteroid-docking-bay off <watch>` (and `cycle`) during a running dump would
cut VBUS mid-transfer. `_busy_guard` consulted `active_op_on_slot`, which reads
only the charge/drain/workbench task registries — while a dump, wanze run or
flash holds the **operation lock**, which lives in the config file precisely so
a separate process can see it.

**What was NOT the gap**, because it looked like it at first: the systemd charge
timer is already covered from the other side — `_web_busy_slots` reads `held`
from `/api/status`, which was #41's fix and is tested. But that only holds while
the web service is up, whereas the lock in the config is readable regardless.
Reading it directly is the stronger check, and the only one an interactive
command has at all.

Fixed by checking `oplock.held()` first in `_busy_guard`, mirroring
`rpcops._refuse_if_busy`. Purely additive: it can only refuse, never actuate.
The test was written failing first, and also pins that an expired lock does not
block.

### N1 · measured, not worth doing · JS fetch helper

78 `fetch` statements, but only 13 near-uniform, splitting into two sub-shapes
of 6–7 one-liners each. A generic `jfetch()` would save a few characters per
site and hide the ones that genuinely differ. Recorded so this is not
re-measured next time.

### F2 · MEDIUM · Escape missed two panels; the panel convention was eightfold — FIXED

Every floating panel is a `<div id="X">` with a `<div id="Xmask">` behind it, and
showing or hiding one is the same three lines. That was written out eight times
— four panels × open/close.

The cost was not the repetition. It was that each new panel had to remember to
join every list by hand, and one didn't: **Escape closed only `reg` and `bt`,
the two panels that existed when the handler was written.** `msgs` and `guide`
were added later and silently stayed open.

`panelShow`/`panelHide` now own the mask convention, and `panelHideAll` finds
panels **by class rather than by a list**, so a panel added tomorrow is covered
without touching the handler. The list is the thing that rotted; not having one
is the fix.

**Honest line count: +6 code lines (+13 with comments).** This consolidation
does not save lines — it trades eight copies of a convention for one definition
and removes a class of bug. Recorded plainly because "lines saved" is the
wrong measure for this one.

### F3 · MEDIUM · the device listing could hang a thread forever — FIXED

`util._run(cmd, check=True, timeout=None)` waits **indefinitely** unless a
caller passes a timeout, and 18 call sites do not. The one that matters most is
`adb_devices_checked` → `adb devices -l`, which runs on every status build: a
hung adb server would block that thread for ever rather than failing.

Bounded at a deliberately generous 20s — far longer than any healthy or
degraded call, so it can only fire where the alternative was hanging. It is
safe to bound precisely because the failure was **already handled correctly**:
`rc != 0` reads as *the call failed* (`None`), not as *no devices*, and
`_wait_adb_state` discards failed samples instead of treating them as watches
that vanished. Both halves are pinned by the test.

### F4 · MEDIUM · `fastboot devices` exists twice, one bounded, one not — REPORTED

`_fastboot_devices()` runs `fastboot devices` with **no timeout**.
`_fb_list_refresh` runs the same command with `timeout=8` and a docstring
warning that the scan takes 5–8s. Two implementations of one listing, with
different hang behaviour and different parsing.

**Not fixed tonight** — deliberately. `_fastboot_devices` feeds
`_wait_for_fastboot`, which is on the **flash path**, and changing its timing
under stress is exactly what this audit refuses to do unattended. It is also
the more interesting half: the two should become one bounded lister used by
both the warmer and the flash wait, with the cache in the caller. That is a
shape decision for mo, not a mechanical edit.

### Checked and clean

- **N2 · oplock release safety.** All three holders release on every path —
  `watch.dump`'s worker in a `finally`, plus an explicit release if the thread
  never starts; the other two are user-driven. No leak.
- **N3 · the wearability floor still holds.** An in-progress drain rate can be
  noisy early and is shown live, which is honest — but it cannot become a
  watch's canonical `est_h`: `_latest_drain_summaries` still enforces
  `_DRAIN_MIN_SAMPLES` and `_DRAIN_MIN_HOURS` (audit B4). Prior fix verified
  real, not assumed.
- **N4 · drain elapsed time is wall-clock** — a clock step skews a run.
  Recorded rather than changed: wall clock is the defensible choice for a task
  that must survive a service restart, which a monotonic clock does not.
- **N5 · slow status refreshes are load-dependent**, not chronic. Not chased —
  optimising without the load present is guesswork; sub-instrument the render
  loop first.

### F5 · MEDIUM · the architecture map had lost twenty modules — FIXED

`docs/ARCHITECTURE.md` still said **0.4**, and described 16 of the package's 36
modules. Missing were `rpcops` (the op table the container split treats as its
security boundary), `rpc`, `oplock` (the cross-process lock), `orbit`,
`registry`, `stockrom`, `wanze`, `icecc` and twelve more.

This is not pedantry. **The map is where someone looks to find out whether the
thing they need already exists** — so an incomplete map is a direct cause of
the duplication this audit was asked to hunt.

All 36 are now described, in their own docstrings' words, and the dependency
section covers `rpc`/`rpcops` and names the one acknowledged cycle. A test now
fails if a module is absent from it — the absence of that test is precisely why
it drifted.

### F6 · LOW · a docstring claims a mirror that does not exist — REPORTED

`webstatus._ssh_battery` says it *"Mirrors `rpcops._reachable_transport`'s
selection"*. It does not: `_reachable_transport` falls back to an **orbit**
member's WiFi address; `_ssh_battery` has only the assigned-SSH branch.

**The code is right and the comment is wrong**, which is the dangerous way
round. Orbit members get their battery from `last_seen` via the warmer, so a
docked-SSH read has no business probing orbit — and someone "aligning the
mirror" would add a network probe per SSH watch per status refresh, which is
exactly the 4.25s render regression `_detect_rndis` was written to remove.

### F7 · LOW · two callers reach past the dispatcher — REPORTED

`cli.cmd_status` and `webstatus.finish_ssh_relocation` call
`DISPATCH._data['op'](args)` directly. `Dispatcher.dispatch()` exists and
raises `RpcError` for an unknown op; the private path raises `KeyError`, so a
renamed op becomes a traceback instead of a clean error. Small and safe to fix,
but entangled with the `webstatus → rpcops` cycle, so it is a shape decision.
