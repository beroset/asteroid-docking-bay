# Pre-1.0 deep audit — 2026-08-16

Autonomous overnight run, authorised by mo: bug hunt plus an architecture
revisit, with **redundancy as the explicit priority** — features were added
subsequently without always checking whether reusable code already existed.
The evening's window-handling consolidation (three drag mechanisms → one) is
the model for what to look for.

**Scope: code only.** The rig is not touched — mo is asleep, the `1-3` cascade
trips under sustained load, and sol/aurora belong to the porting session.

Baseline: branch `onboard-discovery-rework`, version `1.0dev`,
18,253 lines of package + 13,415 lines of tests, 805 tests green.

## Rules this audit holds itself to

- A consolidation must be **behaviour-preserving with existing tests passing
  unchanged**. That is the evening's standard ("the two existing drag tests
  pass unchanged, which is the point").
- If a change would require existing tests to be **rewritten** to pass, it is a
  finding for the morning, not a night action.
- Anything touching **flash, dump or power** paths is a finding, not a fix,
  regardless of confidence. An audit that rewrites the dangerous paths
  unattended is not an audit.
- One concern per commit; suite green, deployed and verified between each.

### F1 · HIGH · the CLI could cut power on a locked watch — FIXED

`asteroid-docking-bay off <watch>` (and `cycle`) during a running dump would
cut VBUS mid-transfer. `_busy_guard` consulted `active_op_on_slot`, which reads
only the charge/drain/workbench task registries — while a dump, wanze run or
flash holds the **operation lock**, which lives in the config file precisely so
a separate process can see it.

**What was NOT the gap**, because it looked like it at first: the systemd charge
timer is already covered from the other side — `_web_busy_slots` reads `held`
from `/api/status`, which was #41's fix and is tested. But that only holds while
the web service is up, whereas the lock in the config is readable regardless.
Reading it directly is the stronger check, and the only one an interactive
command has at all.

Fixed by checking `oplock.held()` first in `_busy_guard`, mirroring
`rpcops._refuse_if_busy`. Purely additive: it can only refuse, never actuate.
The test was written failing first, and also pins that an expired lock does not
block.

### N1 · measured, not worth doing · JS fetch helper

78 `fetch` statements, but only 13 near-uniform, splitting into two sub-shapes
of 6–7 one-liners each. A generic `jfetch()` would save a few characters per
site and hide the ones that genuinely differ. Recorded so this is not
re-measured next time.

### F2 · MEDIUM · Escape missed two panels; the panel convention was eightfold — FIXED

Every floating panel is a `<div id="X">` with a `<div id="Xmask">` behind it, and
showing or hiding one is the same three lines. That was written out eight times
— four panels × open/close.

The cost was not the repetition. It was that each new panel had to remember to
join every list by hand, and one didn't: **Escape closed only `reg` and `bt`,
the two panels that existed when the handler was written.** `msgs` and `guide`
were added later and silently stayed open.

`panelShow`/`panelHide` now own the mask convention, and `panelHideAll` finds
panels **by class rather than by a list**, so a panel added tomorrow is covered
without touching the handler. The list is the thing that rotted; not having one
is the fix.

**Honest line count: +6 code lines (+13 with comments).** This consolidation
does not save lines — it trades eight copies of a convention for one definition
and removes a class of bug. Recorded plainly because "lines saved" is the
wrong measure for this one.

### F3 · MEDIUM · the device listing could hang a thread forever — FIXED

`util._run(cmd, check=True, timeout=None)` waits **indefinitely** unless a
caller passes a timeout, and 18 call sites do not. The one that matters most is
`adb_devices_checked` → `adb devices -l`, which runs on every status build: a
hung adb server would block that thread for ever rather than failing.

Bounded at a deliberately generous 20s — far longer than any healthy or
degraded call, so it can only fire where the alternative was hanging. It is
safe to bound precisely because the failure was **already handled correctly**:
`rc != 0` reads as *the call failed* (`None`), not as *no devices*, and
`_wait_adb_state` discards failed samples instead of treating them as watches
that vanished. Both halves are pinned by the test.

### F4 · MEDIUM · `fastboot devices` exists twice, one bounded, one not — REPORTED

`_fastboot_devices()` runs `fastboot devices` with **no timeout**.
`_fb_list_refresh` runs the same command with `timeout=8` and a docstring
warning that the scan takes 5–8s. Two implementations of one listing, with
different hang behaviour and different parsing.

**Not fixed tonight** — deliberately. `_fastboot_devices` feeds
`_wait_for_fastboot`, which is on the **flash path**, and changing its timing
under stress is exactly what this audit refuses to do unattended. It is also
the more interesting half: the two should become one bounded lister used by
both the warmer and the flash wait, with the cache in the caller. That is a
shape decision for mo, not a mechanical edit.

### Checked and clean

- **N2 · oplock release safety.** All three holders release on every path —
  `watch.dump`'s worker in a `finally`, plus an explicit release if the thread
  never starts; the other two are user-driven. No leak.
- **N3 · the wearability floor still holds.** An in-progress drain rate can be
  noisy early and is shown live, which is honest — but it cannot become a
  watch's canonical `est_h`: `_latest_drain_summaries` still enforces
  `_DRAIN_MIN_SAMPLES` and `_DRAIN_MIN_HOURS` (audit B4). Prior fix verified
  real, not assumed.
- **N4 · drain elapsed time is wall-clock** — a clock step skews a run.
  Recorded rather than changed: wall clock is the defensible choice for a task
  that must survive a service restart, which a monotonic clock does not.
- **N5 · slow status refreshes are load-dependent**, not chronic. Not chased —
  optimising without the load present is guesswork; sub-instrument the render
  loop first.

### F5 · MEDIUM · the architecture map had lost twenty modules — FIXED

`docs/ARCHITECTURE.md` still said **0.4**, and described 16 of the package's 36
modules. Missing were `rpcops` (the op table the container split treats as its
security boundary), `rpc`, `oplock` (the cross-process lock), `orbit`,
`registry`, `stockrom`, `wanze`, `icecc` and twelve more.

This is not pedantry. **The map is where someone looks to find out whether the
thing they need already exists** — so an incomplete map is a direct cause of
the duplication this audit was asked to hunt.

All 36 are now described, in their own docstrings' words, and the dependency
section covers `rpc`/`rpcops` and names the one acknowledged cycle. A test now
fails if a module is absent from it — the absence of that test is precisely why
it drifted.

### F6 · LOW · a docstring claims a mirror that does not exist — REPORTED

`webstatus._ssh_battery` says it *"Mirrors `rpcops._reachable_transport`'s
selection"*. It does not: `_reachable_transport` falls back to an **orbit**
member's WiFi address; `_ssh_battery` has only the assigned-SSH branch.

**The code is right and the comment is wrong**, which is the dangerous way
round. Orbit members get their battery from `last_seen` via the warmer, so a
docked-SSH read has no business probing orbit — and someone "aligning the
mirror" would add a network probe per SSH watch per status refresh, which is
exactly the 4.25s render regression `_detect_rndis` was written to remove.

### F7 · LOW · two callers reach past the dispatcher — REPORTED

`cli.cmd_status` and `webstatus.finish_ssh_relocation` call
`DISPATCH._data['op'](args)` directly. `Dispatcher.dispatch()` exists and
raises `RpcError` for an unknown op; the private path raises `KeyError`, so a
renamed op becomes a traceback instead of a clean error. Small and safe to fix,
but entangled with the `webstatus → rpcops` cycle, so it is a shape decision.

### F8 · HIGH · `charge` had no claim check at all — FIXED (and F1 was incomplete)

F1 guarded `on`/`off`/`cycle`, and I assumed the other `uhubctl_set_power`
sites were legitimately owned by their own operations. Classifying all seven
showed that assumption was wrong.

**`cmd_charge` → `_charge_one` powers a port on and off with neither the
operation lock nor the task store consulted.** During a dump that cuts the
transfer. During a **drain test** it powers the port mid-run, recharging the
watch while the test keeps sampling — which does not fail loudly, it *invents a
result*. That is verbatim the scenario `_busy_guard`'s own docstring says
destroyed five hours of readings.

The systemd timer is a different entry point, guarded from the other side by
`_web_busy_slots`, and is deliberately unchanged.

**The lesson is about F1, not about charge.** F1 was committed as "fixed" while
resting on an unverified assumption about neighbouring call sites. Finishing a
shipped fix outranks finding a new one.

Two testing notes worth keeping: asserting only "no power was switched" let the
planted bug fall into the real charge loop and **hang the suite** rather than
fail — the test now trips a wire on the first call past the guard, so it fails
in milliseconds and says why. And separately, I lost the F5 work once by using
`git checkout` to undo a planted edit on a file with uncommitted changes; every
other plant tonight used a `/tmp` backup, which is the safe pattern.

### F9 · MEDIUM · device strings reached the DOM unescaped — FIXED

Two seams, both carrying data a plugged-in device chooses.

**The guided setup** builds its read-back text from `product`, `serial` and
`path` straight off the bus and interpolated it into `innerHTML` **raw** — so a
USB device whose product string contains markup could run script in the UI. It
is the flow *specifically* for plugging in unknown hardware, which makes it the
worst possible place to trust a descriptor.

**`mkstrip`'s Battery-Info handler** put the serial into a single-quoted JS
string inside an HTML attribute unescaped, while the codename beside it was
escaped and three sibling `openBI` sites already used `jsq()`.

This project already treats a device-supplied serial as untrusted **in a
shell** — the dump command quotes it. The DOM now gets the same standard.
Census: 51 interpolations of device fields, 47 already escaped, 2 URL-encoded,
2 raw; both fixed.

Two testing notes, because both are traps worth naming. The first version of
the serial assertion was **vacuous** — it ran in a harness where the handler
was never rendered, so both assertions passed against absent text. And the
first plant of that bug *also* passed, because it patched one of four `openBI`
sites rather than the one under test. A planted bug that fails to fail is the
only proof that a test is checking what it claims.

### F10 · HIGH · restore assumes one procedure; two proven ones differ — REPORTED

Raised by mo while the audit was running, and confirmed in code.

**Two restores are proven, and they are structurally different.**

| watch | what worked |
|---|---|
| beluga (2026-08-03) | flash `system, vendor, cache, recovery, boot` from the dump **+ the factory's EMPTY `userdata.img`** |
| nemo | the canon **failed**; what worked was `system + boot + userdata + metadata + keystore + cache`, **all from that watch's own dump**, then `fastboot continue`. `misc` is untouchable — its bootloader refuses both erase and flash |

**`restore_plan` cannot build nemo's procedure.** It raises on anything not
classified `firmware`, so it refuses `userdata`, `metadata` (unknown) and
`keystore` (safe_erase). The beluga method is encoded as if it were universal.

**The insight worth keeping:** the safety rule is *not* "never restore userdata
or per-device state". It is **"never restore state from a DIFFERENT unit"**.
nemo's working restore used its own coherent dump; the same partitions from
another watch would have been the unrecoverable case. **Provenance is the gate,
not partition class** — and `fingerprint_gate` already exists to establish it.

Not changed here: relaxing a hard safety stop is not a night edit, and it needs
mo's whitelist first — procedures per watch/family, only **tested** ones
enabled, sibling inference (all LGs, all ASUS) recorded *as inference* rather
than as evidence. beluga is an outlier, and the newer layouts (sol/aurora — GKI
A/B with a dynamic `super`) are untested for restore entirely.

### F11 · mooneye's procedure recovered from the porting transcripts

mo recalled that mooneye was restored during the pike/mooneye Bluetooth work.
Recovered from `meta-smartwatch` session `82e99b58`, 2026-07-06, on mooneye
`M6600TB1Z300` (Mobvoi, Wear OS 8.0 Oreo):

```
fastboot flash boot <stock boot>    OKAY
fastboot flash system <sparse>      FAILED (remote: 'Unknown chunk type')
fastboot erase userdata             OKAY
fastboot erase cache                OKAY
fastboot reboot                     -> stock Wear OS, "tap to begin"
```

**`system` was never written**, and the session says why: *"the existing
/system was pristine stock, and we never needed the sparse flash."* So the
proven path is **boot + erase userdata + erase cache**.

Three device facts belong in the whitelist entry:

- Its **MediaTek `lk` rejects `img2simg` sparse output** — it understands only
  RAW/DONT_CARE, not FILL. Any future `system` write needs a **fill-free**
  sparse image.
- **No separate vendor partition** — `/vendor` is a symlink into `/system`.
- `/data` is **FBE-encrypted, keys in the TEE**, which is *why* erasing
  userdata is right and restoring a foreign one would not be.

One caveat recorded honestly: the boot flashed there was a **modified** stock
boot (`ro.debuggable`, adb_keys baked) for the BT investigation. A pure restore
should use the stock boot from the watch's own dump — the method is proven,
that substitution was incidental.

### Three procedures, three vendors

| watch | vendor | procedure |
|---|---|---|
| beluga | OPPO | 5 partitions from the dump **+ factory EMPTY userdata.img** |
| nemo | — | `system+boot+userdata+metadata+keystore+cache`, **all from its own dump** |
| mooneye | Mobvoi | `boot` + **erase** userdata + **erase** cache; `system` untouched |

Three genuinely different methods. This is the concrete argument for mo's
design: **the procedure must be assigned per watch, never derived.**

### F12 · mo's hypothesis is machine-checkable — and both tested watches confirm it

mo's hypothesis: watches with the **old partition layout and no keystore** can
be restored by simply flashing stock `boot` and erasing `userdata` + `cache`;
nemo needed more only because a botched `fastboot -w` had left it in a state
that required repair, not because the device demanded it. (The RAG agrees: that
sequence is filed under `RECOVERY_WHEN_THE_CANON_FAILS`, not as the canon.)

That is checkable **without touching a watch**: stream the first 32 KB out of
each archived dump and parse its GPT. A 7.65 GB archive costs a few seconds.

**Both tested watches fall on the predicted side:**

- **mooneye — 18 partitions, no keystore** → the simple method is *proven* on it
- **beluga — 40 partitions, has keystore** → the one that *needed* the intrusive recipe

| no keystore — simple candidates | has keystore — not simple |
|---|---|
| mooneye (18) **tested**, pike (13), sparrow (29), wren (29), smelt (29), anthias (33), tetra (35) | catfish (35), firefish (36), ray (36), skipjack (37), tunny (37), triggerfish (38), **beluga (40) tested-intrusive**, belugaxl (40), swift (43), hoki (50), rubyfish (52), sol (81 — A/B + super) |

**Family lines do not hold.** wren and sparrow are 29 partitions with no

### F14 · the dump needs a per-watch procedure table too — at least three methods

From mo, 2026-08-16. Marked proven vs recalled, because only one of the three
has been executed within reach of this record.

**1 · initramfs debug-ramdisk — PREFERRED · PROVEN** (sol, porting session,
2026-08-08)

> Unlock the bootloader; on the **first boot after unlocking**, boot the debug
> ramdisk using the boot image's kernel; dump immediately from the rooted adb
> environment of that ramdisk.

Fewest steps, and **userdata is never mounted** — which is exactly what makes
that image trustworthy per partition rather than only for the quiescent ones.
mo: "that's also why the initramfs method is so much cooler if it's available."

**2 · temp install via /sdcard — mo's description, not verified here**
Applies to watches **without userdata encryption**:

> Unlock the bootloader; let Wear OS restore itself and boot again; re-enable
> adb; push the ext4 to `/sdcard/` on the watch; return to the bootloader and
> `fastboot boot` the boot image.

**3 · beluga temp install — mo's recollection, hedged ("afair")**
As above, but needs **manual intervention** to put the device into the boot
image's recovery sideloading mode.

**Consequence for the whitelist:** dump procedure and restore procedure are
both per-watch properties, so one table should carry **both**. And every method
begins with unlocking the bootloader — so a locked watch cannot be dumped at
all, which is already recorded per serial by `watch.fbreport`
(`bootloader_unlocked`).

Two things I would rather ask than guess: whether methods 2 and 3 differ *only*
by the manual recovery-sideload step, and which boot image "the bootimage" is
in each — AsteroidOS's own, or a device-specific one.

### F15 · dump method is a per-watch capability, and the manual path needs a stepped guide

From mo, 2026-08-16.

**The rule:** where `fastboot boot` of a debug ramdisk is *proven* to work,
always offer that clean method. Otherwise fall back to the runtime dump, which
works on any watch that allows a temp install — what users call **dual boot**.
Initramfs is preferred whenever available.

**The capability model.** Two per-watch booleans decide what is offered, and
neither is derivable from the codename:

- `ramdisk_boot_works` → the clean initramfs dump
- `temp_install_works` → the runtime dump

So they belong in the **same whitelist** as the restore procedure — one table
per watch carrying dump capability, dump procedure and restore procedure.

**The stepped guide.** The runtime dump has several manual steps with the
device changing state between them: unlock, let Wear OS boot, re-enable adb,
push the ext4, return to the bootloader, `fastboot boot`. It needs a guide that
leads step to step **with waiting breaks until the device appears in the
required state**.

**That mechanism already exists.** It is the guided-setup step machine built on
2026-08-15 for onboarding: *instruction → user acts → "Check now" → a hardware
read-back gates the advance, never a ticked box.* Its read-backs are already
the ones this needs — a watch in fastboot, a watch on adb, a watch answering as
root. The step machine generalises from "onboard watches" to **any procedure
with stop points and hardware read-backs**, so this is a reuse rather than a
second implementation.

Needed from mo: which watches have **proven** `fastboot boot` ramdisk support.
That is the whitelist input; sol is the only one this record can confirm.

## Flashing sparrow to 1.0 — three findings from one real task

mo needed sparrow on AsteroidOS 1.0 for the UI agent's audio-chop work. Doing
it surfaced three defects, one of which made the task impossible.

### F16 · HIGH · 1.0 and 2.0 could not be flashed at all — FIXED

The image filenames were hardcoded to the pair the **nightlies** ship:

| channel | boot | rootfs |
|---|---|---|
| 1.0 | `zImage-dtb-<cn>.fastboot` | `asteroid-image-<cn>.ext4` |
| 2.0 | `zImage-dtb-<cn>.fastboot` | `…rootfs.ext4` |
| 2.1 | **both** boot names | `…rootfs.ext4` |
| nightlies (**= 2.2**) | `asteroid-<cn>-boot.img` | `…rootfs.ext4` |

So 1.0 404'd on both files and 2.0 on the boot image — and the failure landed
**at flash time, with the watch already in fastboot**. The channel selector was
offering releases it could not fetch.

Names now come from the release's own `SHA512SUMS`. Boot preference is **zImage
first**, which is not backwards: the new name applies from 2.2 on and 2.1 only
published it early, so zImage is what every *released* channel carries.

**Proven end to end**: sparrow flashed to 1.0 on 2026-08-16 — images
SHA512-verified through a-d-b's downloader, 254 s to write, watch booted and
reports `VERSION="1.0"`.

### F17 · HIGH · the automated flash cannot reach a watch on a direct port — REPORTED

`_flash_one_watch` returns *"not mapped"* without a hub seat and *"non-smart
port"* when the port cannot switch power. sparrow was on a w541 chassis port —
**the only place it enumerates in fastboot** — so the automated feature refused
it, and the flash had to call `_flash_watch` directly.

**This is exactly the no-hub user's situation**, which is a named 1.0 goal: a
user with no smart hub plugs a watch into a laptop port, and a-d-b cannot flash
it. Suggested shape: allow a target that is a bare fastboot serial with no
seat — skip the power-on and the port checks, require the watch to be in
fastboot already, leave the rest of the sequence untouched.

### F18 · MEDIUM · a non-Google bootloader was invisible — FIXED

The bus scan filtered on Google's `18d1` and reported an **empty bus** while
sparrow sat in fastboot as `0b05:7771` (ASUSTek). The pattern: the AsteroidOS
gadget and Wear OS adb both use Google's ID, so one vendor covers every
*running* watch — and hides every non-Google *bootloader*.

Two routes in now: a known vendor ID, **or** a path the caller already knows
holds a watch (the guide passes what fastboot reported). Anything fastboot or
adb can name is a watch by definition, whatever it enumerates under.

mo's point, and it is the right one: Google + ASUS may still miss others —
Mobvoi and Fossil bootloaders are unobserved here. So the table is documented
as **bootloader signatures**, expected to grow, and it makes the scan *faster*
rather than *correct*; the fastboot/adb route is what stops an unlisted vendor
from hiding.

### F19 · LOW · the CLI could not select a release — FIXED

The web UI passed `channel`; the CLI had no option, so a release flash was
reachable only from a browser. `flash --channel 1.0` now matches the selector.

### What the first flash attempt actually was

Not a fastboot fault: the link dropped mid-write (`Status read failed (No such
device)`, then `-71`/`-110` re-enumeration errors on `1-1`). A second attempt
on a stable link went straight through. Worth recording because the 37
errors/minute visible *during the successful flash* were all `usb 1-9` — the
Lenovo dock's own long-standing suspend failures, unrelated to the watch being
flashed. Noise that looks like the event is not the event.

### F17 — FIXED

No-hub flashing is 1.0 scope (mo), so the seat requirement is gone. Without a
hub port there is no VBUS to switch: the power steps are skipped and the watch
simply has to be present. A mapped-but-non-switchable port takes the same path.

A second fault surfaced while fixing it. `_wait_for_fastboot` waits for a
serial that is **new since its snapshot**, so a watch **already in the
bootloader** could never satisfy it — the flash timed out with the device
sitting right there. That is the no-hub user's *normal* state, since they put
the watch into fastboot by hand first. It is now recognised before the reboot
step, by `getvar product` rather than by a seat or an adb serial.

## F20 · The minimal restore is proven on a second device

**sparrow booted to the stock Wear OS pairing screen**, 2026-08-16, from:

```
fastboot flash boot <stock boot from THIS watch's own dump>
fastboot erase userdata
fastboot erase cache
fastboot reboot
```

`system` was never written.

**Why this one counts.** mooneye alone could have been a device quirk. sparrow
is a **different vendor** (ASUS), a **different layout** (29 partitions vs 18),
and was restored from a dump taken in **2023** — so it is the method carrying
this, not the device.

**And the mechanism is now clear.** AsteroidOS installs to `boot` and
**`userdata`**, and never touches `system` — that is literally what
`_flash_watch` does. So on any watch where AsteroidOS lives in userdata, the
stock Wear OS `system` is *still sitting there untouched*. Restoring stock
`boot` and erasing `userdata` is therefore sufficient **by construction**, not
by luck, which is what makes mo's hypothesis predictive for the whole class
rather than a pair of anecdotes.

**Identity beat the filenames.** `original-sparrow.7z` looks canonical and
newer by archive date, but does **not** contain this watch's serial — it is the
remains of the FIRST sparrow, bricked to EDL by a bootloader mishap. The
2023-named `.tar.xz` *does* contain `H1NZCJ010087020`. Established by grepping
each image for the live serial, not by trusting a name or a date. Flashing the
wrong unit's dump is the mistake that killed sparrow #1.

**erase vs format**: `erase userdata` sufficed — Wear OS formatted `/data`
itself on first boot. Worth remembering that erase leaves *no* filesystem while
the factory flow writes an empty one, so `fastboot format userdata` is the
cheap next step if a device ever hangs on spinning balls after this method.

### F21 · MEDIUM · `adb reboot bootloader` hangs, and a-d-b uses that form

On sparrow, `adb -s <serial> reboot bootloader` **never returns** — no error, it
hangs, and the watch does not reboot. `adb -s <serial> shell 'reboot bootloader'`
worked instantly, fastboot ready in 3 seconds.

`ops.py` runs the **hanging** form through `_run(..., check=False)` with **no
timeout**, so `port.bootloader` can block a thread forever — the same class as
the `adb devices` hang fixed as F3. Use the shell form *and* bound it.

### F22 · a stock-restored watch is invisible until adb is switched on

The bus watcher logged `absent` for the full 30 minutes while sparrow booted to
the pairing screen: stock Wear OS with USB debugging off presents **no adb
gadget**. Any guided procedure that restores a watch and then expects to see it
must **stop and wait for the user**, not poll — which is exactly the
"re-enable adb" step in the runtime-dump procedure, and a genuine stop point.
