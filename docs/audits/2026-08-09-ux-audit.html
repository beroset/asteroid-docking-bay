asteroid-docking-bay · design review

The row already knows.

A UX audit of the fleet dashboard. It began as a question about a button row and a crowded menu, and turned up six defects — one of which can put the whole rig on invisible battery drain. The interface is not short of ideas; it is short of one rule applied twice.

01 — what the questions turned up

Six defects, found by asking about layout

These are independent of every visual decision below. They are in the shipped UI now, and each is verified in source rather than inferred.

01

Aborting an onboard sweep leaves every socket dark, silentlysafety

The second confirm's cancel path is {refresh();return;} — but /prepare has already cut VBUS on every socket. Nothing records that the rig is down or offers to restore it, and the link goes back to reading “onboard sweep” in benign green. On this rig that matters more than it sounds: a watch that loses VBUS without a delivered poweroff keeps running on battery, invisible to the host. That is the sturgeon-to-0% failure, fleet-wide.

02

Flash nightly wipes a watch with no confirmationsafety

Flash nightly calls doFl() directly. Flash 2.1 and Flash 2.0 both route through doFlV(), which confirms. Same wipe, opposite treatment — and the unguarded one is the daily driver.

03

A held watch offers a fully-enabled menubug

mkheld paints the badge and _refuse_if_busy rejects every op — but p.held is never passed to menuExecute, so every item stays clickable and the refusal arrives as a toast after the click. The badge exists, the guard exists, the menu simply never consults it.

04

The battery cell is destroyed once per second during a timed chargebug

tickCountdown overwrites #bat-<slot> with a bare span every second, replacing the fill pill. The pill is unclickable during exactly the operation you would want to stop — and it rules the battery cell out as a host for controls.

05

A bootloader watch on an unmapped port is unreachablebug

An empty row's action cell is onboardBtn + mkhide — no menu button. So Fastboot report, Flash, Continue boot and Recovery cannot be reached for the one device that most needs them: one that no longer boots far enough to be identified.

06

A state class died at a rename and nothing noticedrot

The row emits class="btn ex pulsing". The only matching rules are .fillpill.busy.pulsing and .btn-ref.pulsing — and btn-ref appears exactly once in the whole file: inside that rule. Nothing has ever emitted it. The refresh button's blue pulse has been dead since the rename.

02 — the idea worth keeping

Arm, don't confirm

Defects 01 and 02 look unrelated. They are the same defect: a destructive action that commits on a single click, guarded — if at all — by a modal you can dismiss without reading.

The obvious fix is to add a confirm to Flash nightly. That is also the wrong fix, and the adversarial pass argued it down convincingly: this UI already fires blocking confirms for the sweep (twice), the dump, the restore and the pinned flashes. You run these dozens of times in a session. Adding more trains you to click through all of them — at which point the checklist is satisfied, the test is green, and the watch is still wiped.

A destructive control should change state before it acts.

First click arms it and says so on the control itself. Second click commits. The dangerous step becomes a deliberate act rather than a dismissed dialog — and because the armed state is visible, an interrupted operation cannot leave the rig in a state nothing on screen admits to.

That single pattern closes both defects, and it is the only mechanism that fixes the sweep properly. A confirm cannot: the trap in 01 is that power is already cut by the time you decline. Only a control that carries the sweep's lifecycle can tell you the rig is dark and offer to restore it.

03 — the top row

Four kinds of control wearing one costume

Six text links separated by bullets. Between them they contain a view toggle, a persistent fleet-wide policy that rewrites config, two panel openers, and the most disruptive action in the application.

Nothing in the markup distinguishes them — same element, same inline styling, three colours chosen by accident of authorship. And the colours actively mislead: #3fb950 means healthy, on, connected or charging in fifteen places, and it is the colour of the link that cuts VBUS on every socket.

You already wrote the correct rule, four hundred lines above the offence: “bright warning yellow (not the benign green of wifi/bt) — a forced-on screen is a drain, so its ON state should read as an alert.” The header contradicts a principle stated in your own voice.

The gap does more work than the colour. Today the sweep's neighbour is a read-only Bluetooth scan about ten pixels away; afterwards nothing sits within mis-click distance of it.

What I proposed and then killed

A fleet status strip — counts of charging, draining, held, not-enumerating — read well until the adversarial pass checked it. Its premise was that #alert is a permanently blank line to reclaim. It is not. render() writes the screen-forced drain alarm into it; it is empty because the condition is rare, not because it is vestigial. The strip also duplicated the slot gauge that already ships, and would have reintroduced the layout jump that min-height was added to prevent. Killed.

04 — the row menu

Where an action belongs

One menu holds about twenty items in five groups. The rarest and most destructive group sits second, so every trip to Workbench drags the cursor across three ways to wipe the watch.

There is a measurement for how rare: the flash and dump items were silently dead in the UI for two and a half weeks and nobody noticed. Charge or reboot breaking would have surfaced the same day.

The tempting fix is to scatter the menu onto the row's dots, and half of that already ships — the power dot and the wear dot open scoped mini-menus today. But pushed further it fails, for reasons worth recording:

  • The dots are 24px — exactly the accessibility minimum, with no margin — and the mobile breakpoint scales the pills and buttons but never the dots.
  • A single row can carry five visually identical circles. Two open menus, three open a panel. You cannot tell a verb from a link without hovering.
  • The menu is the only surface where the available actions can be enumerated. Shrinking it from 21 items to 9 hides twelve actions behind unlabelled circles whose sole documentation is a tooltip that never fires on touch.
  • Three of the proposed moves would revert decisions that were made, commented, and fenced with a test — including an inline USB toggle removed for being too easy to misclick.

A heuristic, not a rule: an action belongs to the indicator that changes when it succeeds. It is a good tiebreaker and a bad law — it gives no answer for “re-identify” (whose outcome is that the row becomes a different row), three answers for a drain test, and two conflicting ones for a dump.

So the menu keeps its job — it is the enumerable surface — and gains the two things it lacks: an identity, and an honest severity order.

The identity header is the cheapest change in this document and the one I would ship first of the layout work. Four floating menus anchored to 24px circles on a 28-row table is four chances to act on the wrong watch, and the menu currently says nothing about which one it holds.

05 — the vocabulary

223 classes, six ways to look clickable

Clickability is signalled by real buttons, anchors, pills, dots, table cells, and bare spans whose only affordance is the mouse cursor. There is no invariant — you have to hover to find out.

The clearest exhibit is defect 06. A class was renamed, the CSS was not, and a visual state silently stopped existing. Nothing failed, because no primitive owned it. That is the argument for a vocabulary, better than any aesthetic one: unowned styles decay quietly.

The colour contract

Amber currently carries seven distinct meanings — warning, SSH mode, command in flight, running measurement, held, over-subscribed, mid battery. A watch in SSH mode, a watch mid-command, a watch under an oplock and a watch at 40% are all the same colour.

Four changes with no visual consequence

These are the cheapest wins in the audit — pure deletion, zero rendering change, and each one makes the contract above enforceable rather than aspirational.

  • Drop ~20 redundant border-color declarations. .cbadge, .sdot and .smt declare border:1px solid with no colour, so currentColor already applies. Every variant that writes border-color:X;color:X is saying X twice.
  • Delete ten dead rules. They are not merely unused, they are decoy vocabulary: .hrb is amber-for-reboot while the live .menu-item.rb is orange-for-reboot. Anyone normalising from the CSS would pick the wrong one.
  • Collapse .smt into .cbadge. They are byte-identical apart from declaration order — and the mobile breakpoint scales one twin and not the other, so they visibly diverge under 720px.
  • One pulse keyframe. “Busy” is currently five different pulses at five periods; nothing tells you whether a 1.4s dim means draining, screen-forced or wanze.

Eleven inconsistencies should stay. Green is reserved for power so Smart is deliberately blue; the forced-screen toggle is deliberately not green; menu items are deliberately text links; wear is deliberately the one pink button; .mtemp deliberately colours nothing below the silicon limit because a lower threshold would cry wolf on two of three nodes. Each is documented in your own comments. A normalisation pass that flattens them would be a regression wearing a tidy-up's clothes.

06 — what nobody proposed

Two power controls, and the dangerous one is the obvious one

This came out of the adversarial pass, and it outranks everything above.

Every row carries two controls that look like power. The large, colour-coded toggle in the port cell cuts VBUS. The small grey circle beside it opens watch power actions — halt, reboot, bootloader.

Per this project's own hardware rule, and per the code's own comment: cutting VBUS on a running watch does not stop it. It keeps draining on battery, invisible to the host. That is how sturgeon reached 0%.

The big obvious control is the unsafe one. The safe one is a 24px circle with no label.

Nothing in the row says which is which, and the scattering proposal would have loaded more verbs onto the small circle while leaving the large one untouched.

I am not proposing a fix here, because the right one depends on a judgement only you can make: whether the VBUS toggle should ever be one click on a watch that is running. The options are to label the pair by scope, to make the toggle arm-then-commit when the watch is live (the same pattern as section 02), or to route it through the graceful path by default and keep the raw cut as an explicit override.

07 — sequence

What to do, in order

Ordered by consequence closed per unit of change. The first four are defect fixes and need no design decision from you at all.

  1. Make the sweep stateful. closes defect 01
    Arm → armed (all sockets off, with restore) → sweeping → idle. The only fix that can tell you the rig is dark after an abort.
  2. Arm the flash items instead of confirming them. closes defect 02
    And pin it: a danger-tier item that can commit on one click is a build error. This repo already has the static-contract test genre for exactly this.
  3. Pass p.held to the menu and disable with the reason. closes defect 03
  4. Re-render the battery pill in tickCountdown instead of overwriting the cell. closes defect 04
  5. Give an unmapped row its menu button. closes defect 05
    A watch in the bootloader on an unidentified port currently has no route to Fastboot report or Continue boot.
  6. The four no-visual-change CSS deletions. closes defect 06
    Redundant borders, dead rules, the duplicate pill primitive, one pulse keyframe.
  7. Menu identity header. cheap · high value
    Every floating menu names its watch. No test conflicts, purely additive.
  8. Severity order in the menu — capture tier, danger rail, wipes-the-watch heading.
  9. Header rail — group by kind, quarantine the sweep behind a real gap, retire green from it.
  10. The colour contract, applied outward from danger red — the one token that is already unambiguous.
  11. Then, and only then, the argument refactor — replace the 13 positional args with the slot. It is not an enabler, it is a dependency inversion that turns three cheap unit tests into integration tests. Do it after the UI work, not before.

Three things I told you that were wrong.

I said the breakpoint was 448px. There is one breakpoint and it is 720px; I had misread a line number as a pixel value.

I passed along that #alert is a permanently blank line worth reclaiming. It is not — render() writes the screen-forced drain alarm into it. That misreading was the entire load-bearing premise of the status strip, which is why the strip is dead.

I relayed that the stats dots are 14px. They are 24px; 14px is the glyph inside. The argument for hanging verbs on them was made against the wrong target size — and at 24px they sit exactly on the accessibility minimum with no margin, which strengthens the case against.

Nothing in this document is implemented. The counts come from a careful pass over the served template rather than rough greps: 223 class names, ~50 buttons, 21 anchors, 44 onclick handlers on bare elements, 14 keyframes, ~62 distinct hex colours.

postscript — what shipped

All of it, and what the audit got wrong

Written the same day the audit was read. Everything below is implemented, deployed on the rig and pushed; the suite went from 765 tests to 779, and every fix is validated by planting the bug it exists to catch.

Read sections 03–06 as history. They describe the UI as it stood before this work. The mockups there are proposals, not the current interface.

The six defects

  • 01 — the sweep has a lifecycle. Armed states plainly that every socket is off, and offers Restore power; a new onboard.sweep_restore op powers them back one at a time. Aborting can no longer drain the fleet in silence.
  • 02 — destructive items arm before they commit, and doFlV’s confirm is gone rather than leaving two mechanisms for one job.
  • 03 — a held watch says what holds it, with its actions disabled and the reason given.
  • 04 — the countdown writes inside the pill, so the battery control survives a charge.
  • 05 — an unmapped bootloader port gets a menu; Flash stays out because it needs a codename mapping.
  • 06 — the dead pulse is alive, eight decoy rules are gone, .smt collapsed into .cbadge, and a test now fails if any state class is styled but never emitted.

Beyond the audit, at moWerk’s direction

  • The status row carries persistent state only; the sweep moved to the registry panel.
  • The port toggle opens a scoped menu — and cutting VBUS on a live watch arms first, because that is the case that strands one on battery.
  • Duplicated actions went to the surface that already showed them: Power to the dot, USB mode to Connect, Set time to Settings, Screenshot to the live view. Notify was the exception — it was not duplicated anywhere, so it moved to Vitals beside Buzz rather than being deleted.
  • The drain test moved to Workbench; wanze gained a Deploy/Remove item and a true uninstall that removes every file install pushed, while keeping the trace unless asked.
  • Amber gave back five meanings it should never have carried.

What the audit got wrong

The worst call was a severity, not a fact.

The adversarial pass found that hub headers were keyed by their visible label, and flagged it as a low-severity edge case — two hubs renamed identically, reachable via the rename pencil. I recorded it that way and did not fix it.

It was not an edge case. Auto-naming gives every chip in a physical box the same name, so it was the normal state of every multi-chip box on the rig: the Sabrent is five hub entries all labelled Sabrent, and reconcileRows drops a repeated key, so four of its five headers silently never reached the DOM.

It surfaced the way these things do — moWerk clicked hide on the Sabrent, saw nothing happen, kept clicking, and watched rows vanish four at a time. Two bugs behind one symptom: the collision hid the headers, and hiding acted on one chip at a time when a box is five, the first of which carries no ports. Both are fixed.

The lesson is not that the finding was missed. It was in my hands, correctly described, and I rated it wrong — a severity assigned from how obscure the trigger sounded rather than from how the rig is actually configured. The three factual corrections in section 08 stand as written.

One process note worth keeping: the static shell-quoting test caught an unquoted 2>/dev/null in the wanze uninstall that would have redirected on the host instead of the watch, and test_served_js_parses caught a backslash eaten by the Python string layer — the trap this file warns about, sprung while fixing it.
